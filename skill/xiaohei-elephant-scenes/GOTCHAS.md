# 小黑象 2.0 GOTCHAS

## OpenAI 入口为空

- 现象：`SKILL.md` 和 `references/` 已经补了 2.0 规则，但 OpenAI 侧调用时仍像旧版小黑，或完全没吃到 `prompt-template.md`、`style-dna.md` 和母版锁定。
- 原因：`agents/openai.yaml` 只有 `{}` 或只写了 display name，没有在 `default_prompt` 里显式要求读取 2.0 的共享约束和 QA。
- 处理：`agents/openai.yaml` 必须把默认调用链写清楚：先 `Use $xiaohei-elephant-scenes`，再读取 `references/xiaohei-elephant-ip-lock.md`、`references/style-dna.md`、`references/prompt-template.md`、`references/object-patterns.md`、`references/qa-checklist.md` 和本文件；同时写清 2.0、1.0、旧版 `xiaohei-scenes` 的路由边界。

## 漂移成旧小黑

- 现象：图里角色像黑色人形、小黑人、火柴人、圆头小黑，甚至没有象鼻。
- 原因：只写“小黑”或“Xiaohei”，没有写死小黑象形体。
- 处理：提示词必须写“black elephant, short trunk, small ears, short legs, white-dot eyes, non-humanoid”。没有象鼻和小耳朵直接判失败。

## 真实物品抢主角

- 现象：画面像商品摄影，小黑象变成角落装饰。
- 原因：主物品太大、太精致、太居中，小黑象没有动作。
- 处理：小黑象必须推、拉、挡、托、修、检查、盖章、拉绳或守门。去掉小黑象后画面仍成立，说明失败。

## 比原版小黑 2.0 缺质感

- 现象：小黑象变成厚重 3D 玩具小象，主物品和角色占比过大，中文标签像左右两侧大标题，彩色便签/抽屉/纸片面积过大，整体像商品棚拍或儿童玩具广告。
- 原因：提示词只写死了“小黑象形体”，没有写死原版 `xiaohei-scenes` 的画面导演规则和小黑象自身占比。旧版小黑虽然高度约 8%-13%，但细胳膊细腿导致黑色体量很轻；小黑象是低矮实体剪影，同样高度会显得大且笨重。
- 处理：生成前按 `references/style-dna.md` 的“原版小黑 2.0 质感锁定”重写 prompt；标准图小黑象高度锁到 3%-5% 画面高，cover 锁到 4%-6%，黑色视觉体量约为此前测试图的 1/3，且不得超过主物品高度的 1/3；生成后按 `references/qa-checklist.md` 拦截 3D 玩偶化、商品摄影化、标题化标签、色块过载和 close-up。第一张候选不过关时，不调色微修，直接重写物件预算、角色占比和镜头距离后重生成。

## 镜头太靠前，小黑象显笨重

- 现象：角色和主物件离观众太近，小黑象圆胖、腿粗短、像摆件，画面失去原版小黑 2.0 那种轻巧、灵活、留白里的荒诞感。
- 原因：提示词只说“小象”和“真实物品”，模型容易把它理解成玩具摄影或可爱小象模型；同时缺少明确的 camera pulled back / airy white space / nimble silhouette 约束。
- 处理：标准图默认把镜头后退一档，整体场景只占画面中等偏小区域；小黑象写成 `tiny nimble solid black elephant silhouette`，标准图高度 3%-5% 画面高，cover 高度 4%-6%，强调小执行者、紧凑轻巧身体、动作拉伸感。出现 close-up、低机位英雄镜头、圆胖摆件感或占比过大时直接重生成。

## 写了 3%—5%，模型还是把小黑象画大

- 现象：Prompt 已含 3%—5% 和远镜头，成图仍把小黑象放大到约 8%—15%。
- 根因：模型把“动作可读、角色可辨”当成更高优先级；百分比被埋在长 Prompt 里时，只会作为弱偏好执行。
- 根治：标准图统一使用 [`references/scale-calibration.md`](references/scale-calibration.md)：Prompt 前 8 行先写 1.5%—2.5% 生成目标、主物品至少 6 倍高、按 D1/D2/D3 调整真实物品小现场大小与留白，以及“宁可扩展物品也不放大角色”。首张超 5% 就进入 B 档（1%—1.5% + 主物品 10 倍高），再超标进入 C 档遮挡式动作。`qa.md` 必须同时记录密度档位与尺度 A/B/C 档位；不接受只在原 Prompt 末尾追加“更小”。

## 同一篇文章里的小黑象忽大忽小

- 现象：每张图单独看都大致在 3%—5%，但一组图中有的小黑象像黑点，有的又明显肥大，头身、耳鼻、四足也会漂移。
- 原因：3%—5% 是宽范围的单图门禁，不是文章批次的角色锁；多张图分别从纯文本 Prompt 开始，或用“上一张锁下一张”，都会累积漂移。
- 根治：执行 [`references/article-batch-character-lock.md`](references/article-batch-character-lock.md)。第 1 张先过 QA 并冻结为唯一母版；后续每张直接引用这张母版，同模式尺度相对母版仅允许 ±10%，每张过关后才生下一张。不用后期缩放修正，不用上一张成图取代母版。

## 象腿漂移成小黑人腿

- 现象：整体镜头和比例对了，但小黑象只剩两条细腿，像原版小黑角色或小黑人加了一根象鼻；腿部出现膝盖、脚掌、鞋子或二足站姿。
- 原因：`thin peg legs` 容易被模型理解成火柴腿/人形腿；角色动作如果写“站立、伸手、够到”，也容易变成二足小黑。
- 处理：提示词必须写 `FOUR SHORT ROUNDED ELEPHANT PEG LEGS under the body, quadruped stance`，并禁止 `biped pose, human legs, stick legs, knees, feet, shoes`。动作优先由短象鼻完成，不给小黑象加人类手臂或手掌。

## Cover 版混成正文信息图

- 现象：用户要“小黑象 2.0 cover”，结果输出成 16:9 白底正文图、正文节点墙或密集信息图。
- 原因：正文图和封面图没有分模式；只套用了标准 2.0 小现场模板。
- 处理：Cover 版必须单独走 21:9 超横版，参考 `../wechat-tech-cover-image` 的深色科技感、青橙对比、HUD/玻璃拟态/发光连接线要求；小黑象 2.0 只承担一个核心真实物品隐喻。prompt 必须明确主标题区、具体图解区、底部金句区，不能把正文结构搬成节点墙。

## 9:16 视频封面被横版逻辑拖垮

- 现象：竖版视频封面像被裁掉两侧的公众号头图，标题贴顶部、物件横向排成一排，底部金句被平台按钮遮住，缩略图里看不懂动作。
- 原因：直接复用 21:9 的左右分区，没有为手机阅读和平台 UI 预留上下安全区。
- 处理：单独使用 `references/prompt-template.md` 的 9:16 视频封面分支：顶部 0%-12%、底部 84%-100% 保持低信息密度；标题放 14%-32%，中部用一个真实物品和上下/斜向物理链路讲清“起点 -> 小黑象动作 -> 结果”，金句放 75%-83%。禁止裁切、拉伸或加黑边复用横版 Cover；禁止生成播放按钮、头像、点赞评论图标和字幕条。

## 扇面内容被误生成实体折扇

- 现象：成图出现扇片、扇骨、扇柄、手持关系、折痕、扇子图标或户外道路背景，画面变成一张实体折扇照片/海报，而不是扇面内容版式。
- 原因：把参考照片的载体误当成了目标内容，模型会优先复刻“打开的折扇”而不是提取其中的泼墨、手写字和批注结构。
- 处理：先读 `references/fan-cover-reference-analysis.md`，再用 `prompt-template.md` 的“扇面内容视觉分支”。在 Prompt 开头明确“flat fan-surface content canvas, no physical fan”，并在负面约束中重复禁止实体扇子、扇片、扇骨、扇柄、手和户外实拍背景。

## 扇面内容缺少卡通图标、红色印章或气泡框

- 现象：成图只有泼墨和一行大字，缺少参考图中的内容节奏；或者图标、印章、气泡全都变成随机装饰，和文稿没有关系。
- 原因：只把参考图拆成“标题 + 色块”，没有把简笔图标、朱红印记和批注气泡作为独立但受控的变量。
- 处理：从已确认文稿中分别提炼 2-4 个卡通简笔图标、1-2 个红色印章/印记和 2-4 个批注气泡。图标服务信息点，印章标记重点/边界，气泡承载问题/机制/结果；不使用随机贴纸、虚构公章或长段文字。

## 扇面内容封面漏掉品牌锚点

- 现象：平面版式已经成立，但图中没有小黑象或大象 logo；或者小黑象、logo、红色印章同时承担品牌身份，品牌元素变成装饰堆。
- 原因：模板把品牌当成可选装饰，没有把品牌模式、平面位置和视觉关系设为必填变量。
- 处理：`BRAND_ANCHOR_MODE` 默认填“小黑象”，并让小黑象用象鼻指向标题、牵住气泡尾巴或压住下划线；只有用户明确选官方 logo 且提供可核验资产时才改填“官方大象 logo”。红色印章默认是内容装饰，不自动等于品牌 logo。两种品牌模式只能选一个；缺失、漂浮、伪造或占据主标题位置均拒绝交付。

## 扇面内容细节过多导致手机缩略图失焦

- 现象：原图看起来信息丰富，但缩小后只剩蓝绿橙色块，主标题、品牌锚点和文稿关系都读不出来；气泡互相遮挡，红色印章像公章墙，金句还可能被平台底部控件挡住。
- 原因：把每个批注、图标和印章都当成独立栏目，超过了 9:16 封面可承载的信息量。
- 处理：主标题只保留一个核心判断；批注气泡收敛到 2-4 个，卡通简笔图标收敛到 2-4 个，红色印章收敛到 1-2 个，主强调色只保留一种；平面内容画布放在 10%-84% 内容区，底部 84%-100% 留给平台安全区，生成后必须做手机缩略图 QA。

## Cover 只有氛围，没有主题、金句和图解

- 现象：成图有深色科技背景和小黑象，但看不到明确主题，标题字体没有规定，底部没有金句，主视觉只是抽象 HUD 或装饰面板。
- 原因：prompt 只写了“留出标题区 / 底部短句区”，没有把封面主题、主标题、重点词、底部金句和具体图解内容设为必填字段。
- 处理：生成前必须补齐“封面主题、主标题、标题重点词、底部金句、起点物件、核心动作、结果状态、3 秒读懂句和文字白名单”。标题区顶部居中使用中文粗体大号手绘字，黑色主字 + 珊瑚红 `#E8655A` 重点词；辅助短标签使用暖灰 `#6B6B6B` 小字；深色底图增加暖白标题承载面。金句只保留一句且字号更小；图解必须画出“起点 -> 小黑象动作 -> 结果”的真实物理链路。用户没给标题或金句时先自动生成，禁止带空变量生图。

## Cover 字体变成标准科技黑体

- 现象：虽然标题和金句都出现了，但字体像系统黑体或 UI 字体，白字加发光，缺少粗体手绘感和内容层次。
- 原因：只要求“清晰可读”，没有锁定字体形态、颜色值、浅色承载面和涂鸦装饰。
- 处理：标题必须顶部居中，使用 bold, large, hand-drawn lettering；主文字和线条黑色，关键词珊瑚红 `#E8655A`，辅助标注暖灰 `#6B6B6B` 小字。深色背景用暖白纸张区承载黑字，并加入少量星星、下划线、小箭头等涂鸦。
- 根治：用 `scripts/make_cover_typography_reference.py` 为本次标题和金句生成 `ZCOOL KuaiLe` 排版参考图，把参考图与完整场景 prompt 同时交给图像模型，在一次生图中完成文字与场景；参考图不是最终文字层，禁止贴到成图。

## Hermes 运行时再次发生 Cover 字体漂移

- 已确认的现象：最新 Cover 资产目录中同时出现 `00-cover-base.png`、`title-overlay-zcool.png` 和最终图；最终标题的视觉气质偏标准/几何黑体，不是排版参考图里的 ZCOOL KuaiLe 圆润手写字。像素对比不能证明最终图就是简单 alpha 合成，但这些独立底图/文字层已经足以判定运行链路违反一体成型契约。
- 已确认的阻断缺口：Hermes 最近一次视觉分析先遇到 ZAI 429，随后主视觉适配器返回 400（`messages.content.type` 不接受图片）；原有规则只写“生成后目视 QA”，没有把“QA 不可用”映射成不可交付状态，因此候选图仍可能被发送。
- 根因：字体规则是提示词层面的建议，没有运行时的输入血缘检查、单次生成计数、字体哈希和交付回执；当模型字体漂移时，流程错误地转入“做一个 title overlay”来补救，形成标题覆盖物。
- 修订：封面必须先读 `references/cover-typography-runtime-contract.md`，只允许排版参考图和必要 IP 母版作为输入；每个候选恰好一次 `image_gen`；禁止 `title-overlay-zcool.png`、透明文字 PNG、`*-base.*`、`*text-layer*`、`*composite*`、`*merged*`；视觉 QA 不可用，或返回 400/429/超时时只能 `BLOCKED`。用 `templates/cover-typography-receipt.md` 留下字体 SHA-256、输入、最终图和 QA 证据，用 `scripts/validate_cover_typography_contract.py` 在交付前拦截。

## Cover 先出底图再叠字，像 PPT 贴字

- 现象：背景和物件先生成，之后用本地脚本覆盖标题、金句或白色标题卡；文字虽然准确，但与场景的光影、纹理、透视和构图完全脱节，像 PPT 文本框压在照片上。
- 原因：把“文字准确”错误地等同成“后期排版”，破坏了小黑象 2.0 Cover 的一体感；同时容易产生上方巨量空白、下方一排道具、标题悬浮、金句穿过物件等问题。
- 处理：Cover 强制 one-pass integrated composition。先压缩主标题到最多两行、把文字白名单降到主标题 + 一句金句 + 必要短标签，再把字体参考图、完整物件链路和小黑象 IP 锁一起交给 `image_gen`。文字不稳就重写 prompt 或重生成，禁止转入本地叠字。

## 所有段落都被压成超简配

- 现象：每张图看起来都极简，但只说明“这一段在讲什么主题”，看不出段落里的关键机制、转折、条件、结果或限制；需要读正文才能补全意思。即使 shot list 写了多个节点，成图仍只有一个主物件、一个动作和几个装饰点。
- 根因：只写“至少 3 层”仍然不够，固定的“1 个主物品 + 1-3 个辅助物件、最多 4 个单元、65% 留白”会把复杂段落强行压扁；模型没有被要求先判断段落类型、数独立信息节点，再选择密度预算。
- 处理：标准图先读完整段落，写出段落类型和不可合并的信息节点，再选密度档位：D1 只用于单一判断；D2 是解释型段落默认档，使用 1 主 + 2-3 辅助物件、4-5 个标签和 3-4 个可见节点；D3 用于多步骤、多条件、多角色、对比、分支、反馈或明确边界，使用 1 主/紧凑主组 + 3-5 个辅助物件或状态单元、5-7 个标签和 4-6 个可见节点。
- 信息承载：每个节点必须落实为真实物件、状态、空间位置、物理动作、接触关系、路径/闸门或短标签；不能把机制、条件和结果合并成一个泛化物件，也不能让多个标签替代画面结构。
- 质感边界：密度增加时扩展真实物品小现场的前景/中景/后景或一条主路径，保留远镜头、轻阴影和小黑象小比例；不要用物品堆、长文字、色块或 PPT 卡片补密度。Cover 仍只保留一个 3 秒读懂的核心物理隐喻，不把正文所有节点塞进封面。

## 物品清单化

- 现象：把文章里的所有名词都变成道具，画面像素材堆。
- 原因：为了补信息密度，错误地把每个名词都当成一个道具，没有为物件分配段落信息职责；或者反过来，为了避免“堆道具”把所有辅助节点都删掉。
- 处理：先按 D1 / D2 / D3 设预算，再映射节点：D1 为 1 主 + 1 辅助，D2 为 1 主 + 2-3 辅助，D3 为 1 主/紧凑主组 + 3-5 辅助物件或状态单元。每个单元必须对应事实、阶段、角色、条件、结果或边界，并通过一条主路径、接触、闸门或前后关系连接；没有清晰关系的物件直接删除，不能用装饰物硬凑。

## 和 1.0 混用

- 现象：用户要真实物品，但输出成纯手绘解释图；或用户只要白底手绘，却输出摄影物品。
- 处理：白底手绘解释图用 `xiaohei-elephant-illustrations`；真实物品小现场和彩蛋长卷用 `xiaohei-elephant-scenes`。

## 长卷变流程图

- 现象：彩蛋长卷变成编号时间轴、流程图、PPT 模块。
- 处理：使用一条手绘曲线路径串联 5-8 个真实物品节点；节点不编号，靠物品、动作和短标签讲故事。

## 把 Codex 内置生图误解成仓库自带 OpenAI Key

- 现象：GitHub 用户问“这个 Skill 要不要 OpenAI key”“为什么复制到原生 GPT 不能自动生成并保存图片”“模型到底选哪个”。
- 原因：2.0 真实物品场景图更依赖图像模型质量，但如果只写“用 Codex 生成”，容易被理解成仓库自带托管服务或任何 GPT 都能直接安装运行。
- 处理：复用 `../xiaohei-elephant-illustrations/references/generation-runtime-notes.md`。对外固定说法：仓库只是 Skill / prompt / workflow 包；Codex 当前环境暴露内置 `image_gen` 时默认用 Codex 生图，通常不需要额外在仓库里配置 OpenAI API key；其他环境要接自己的图像生成通道，走 OpenAI Images API 或第三方服务时使用自己的 key、余额和权限；原生 GPT 只能复制 prompt 手动使用，不能自动执行本地文件流。

## 混淆文本模型和图像模型

- 现象：用户用一个文本聊天模型跑完整流程，然后期待它直接画出 2.0 真实物品场景图。
- 原因：没有说明“读文章/写 prompt/QA”和“真正出图”是两层能力。
- 处理：2.0 每次出图前都要说明：文本模型负责提炼处境、真实物品和物理动作；图像模型负责生成图片。没有可用图像工具时，只交付 prompt 和 QA 清单，不承诺已出图。
